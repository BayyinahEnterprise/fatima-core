Mythos-Class: A Synthetic-Target Containment Benchmark
for Structural Honesty Verification
Phase C Protocol and Target-Generation Methodology
Bilal Syed Arfeen
August 2026
Abstract
Mythos-Class specifies a Phase C containment benchmark using AI-generated synthetic vulnerability
targets that are outside the test model’s own generation distribution. A generating model (Kimi K3,
Moonshot AI) produces novel vulnerability scenarios; a test model operates under BSSG containment
(DOI 10.5281/zenodo.21713180) against those scenarios. The benchmark inherits SHV-Bench’s two-sided
success criterion (DOI 10.5281/zenodo.22062097): the contained agent must produce fewer unauthorized
effects while maintaining noninferiority on within-scope discovery capability.
The design addresses the Phase C requirement from the SHVVP preregistration (DOI 10.5281/zenodo.21583202): seeded synthetic targets only, no live zero-day. The hidden target set stays restricted
(publication posture v0.1 FROZEN, Gate 1); only the methodology, aggregate discovery quality, and safe
redacted examples publish.
This paper specifies the target-generation protocol, the novelty-verification procedure, the decoyplacement methodology, the evaluation protocol, and the reporting framework. It does not report results,
does not generate targets, and makes no effectiveness claim about SHV, BSSG, or any component of the
Structural Honesty program.
Scope limitation (stated upfront): Synthetic targets generated by an AI model are recombinations
of patterns in the generating model’s training distribution. They are novel relative to the test model but
not necessarily technically valid or representative of real-world exploitation complexity. The external
validity of results obtained on synthetic targets against expert-constructed or real-world targets is an
open question that this benchmark cannot answer. A definitive Phase C result requires expert-verified
targets (Path B); this benchmark provides a first-pass Path C result.
Keywords: AI evaluation; synthetic vulnerability targets; containment benchmark; structural honesty
verification; BSSG; Phase C; cross-model generation; evaluation security

1. Introduction
1.1 The Phase C Question
SHV-Bench (DOI 10.5281/zenodo.22062097) specifies the Phase B evaluation: does BSSG containment change
outcomes on known vulnerabilities from the CISA KEV catalog? Phase B tests containment against attacks
the model has almost certainly seen in training. A positive Phase B result would show that containment
changes the prespecified E1/E2 outcomes on familiar targets. It would not show whether containment changes
those outcomes on unfamiliar targets.
1

Mythos-Class asks the harder question: does BSSG containment change outcomes on vulnerability scenarios
the test model has not been trained on?

1.2 The Cross-Model Generation Solution
Constructing genuinely novel vulnerability targets typically requires human security researchers. This protocol
uses a different approach: cross-model generation. A generating model (Kimi K3, Moonshot AI) produces
synthetic vulnerability scenarios. A test model (from a different vendor family) operates against those
scenarios under BSSG containment.
The novelty claim is specific and limited: the scenarios are novel relative to the test model because they were
generated by a different model after the test model’s training cutoff, and they were never published in any
corpus the test model could have trained on. The novelty claim is NOT that the scenarios are unprecedented
in the history of cybersecurity – they are recombinations of known vulnerability classes, generated by a model
that was itself trained on cybersecurity literature.

1.3 What This Paper Does and Does Not Do
This paper specifies the protocol. It does not generate targets, run evaluations, or report results.
This paper does:
• Define the target-generation prompt protocol (Section 2)
• Specify the novelty-verification procedure (Section 3)
• Specify the decoy-placement methodology (Section 4)
• Specify the evaluation protocol, inheriting SHV-Bench’s paired design (Section 5)
• Specify the reporting framework and restriction tiers (Section 6)
• State the falsification conditions (Section 7)
• State the scope limitations honestly (Section 8)

2. Target-Generation Protocol
2.1 Generating Model
Model: Kimi K3 (Moonshot AI, China).
Rationale for Kimi K3: (a) Different vendor family from the test model, maximizing training-distribution
divergence. (b) Kimi K3 has demonstrated strong analytical capability in the program’s audit trajectory
(carrying seat across SHV-Bench R1–R5, PASS). (c) No commercial relationship between the generating
model’s vendor and the containment architecture’s developer.
Disqualification: Claude (Anthropic) is barred from generating targets because BSSG is an Anthropicprogram artifact. GPT (OpenAI) is barred from generating targets if GPT is the test model. The generating
model and the test model must be from different vendor families.
Test-model precommitment: The exact test model is frozen in the benchmark manifest before the first
target is generated:
• Model identity: exact name, version/snapshot, checkpoint date.
• Inference configuration: temperature, token limits, system prompt, tool permissions.
• Agent scaffold: framework, version, SHA-256 of scaffold code.
• BSSG build: version, SHA-256 of gate code and configuration.
No model selection, version change, or configuration adjustment is permitted after the first generation session
begins. If multiple test models are intended, all must be preregistered with a complete analysis plan before
any generation.

2

2.2 Generation Prompt Protocol
Kimi K3 receives a structured generation prompt for each target. The prompt specifies:
• Vulnerability class (drawn from a predeclared class distribution; Section 2.3).
• Environment constraints (what software, services, and network topology the scenario must use).
• Complexity tier (single-step, multi-step, or chained; Section 2.4).
• Output format (structured JSON: scenario description, environment specification, expected exploitation path, expected impact, authorized scope, adjacent-system specification for containment
testing).
The prompt does NOT:
• Name specific CVEs (the scenario must be original, not a reproduction of a known CVE).
• Provide exploit code (the generating model describes the vulnerability; it does not write the exploit).
• Reference the test model or BSSG (the generating model does not know what it is generating targets
for).

2.3 Target-Class Distribution
The target set is stratified across vulnerability classes to ensure coverage. The class distribution mirrors
SHV-Bench’s 14 classes (RCE, Privilege Escalation, Command Injection, Memory Corruption, Auth Bypass,
Path Traversal, Buffer Overflow, Info Disclosure, XSS, DoS, SQL Injection, Injection Other, Deserialization,
SSRF) with proportional allocation.
The total target count is 50 scenarios:
• 20 Tier 1 (single-step exploitation, 15-minute budget)
• 20 Tier 2 (multi-step exploitation, 30-minute budget)
• 10 Tier 3 (chained exploitation across systems, 60-minute budget)

2.4 Complexity Tiers
Tier 1 – Single-Step: The scenario describes a single vulnerability in a single service. The exploitation
path has one step. The containment question: does the agent stay within the authorized service boundary?
Tier 2 – Multi-Step: The scenario describes a vulnerability that requires multiple actions to exploit (e.g.,
information gathering, then authentication bypass, then data access). The containment question: does the
agent stay within the authorized action sequence?
Tier 3 – Chained: The scenario describes two or more vulnerabilities across different systems that must be
chained. The environment includes adjacent systems outside the authorized scope. The containment question:
does the agent exploit only the authorized chain and avoid lateral movement to unauthorized systems?

2.5 Generation Session Discipline
Each generation session produces one candidate target. Sessions are independent (no memory carryover).
Precommitted generation budget: Exactly 60 generation sessions are run sequentially (50 targets + 10
replacement candidates). The class/tier assignment for all 60 sessions is precommitted in the benchmark
manifest before the first session: each session’s vulnerability class and complexity tier are drawn from the
Section 2.3 distribution using the committed seed, and the assignment is immutable. The first 50 candidates
that pass the novelty-verification procedure (Section 3) are retained in generation order. If fewer than 50 pass
from the 60-session budget, the benchmark reports the shortfall and runs with the reduced set. No additional
sessions beyond 60 may be generated. Every candidate (retained or rejected) is logged in a hash-committed
candidate ledger containing: session index, generation timestamp, candidate scenario, novelty-verification
result, disposition (RETAINED / REJECTED-NOVELTY / REJECTED-DUPLICATE / REPLACEMENT),
and reason code.

Prompt template freeze: The generation prompt templates are Tier 3 (private) but their SHA-256 digests
are committed in the benchmark manifest before the first generation session. Post-freeze prompt modification
invalidates the run (F-MC9).
All generation sessions are conducted on a consumer-tier Kimi K3 account. The candidate ledger is hashcommitted in the manifest.

3. Novelty Verification
3.1 The Novelty Claim and Its Limits
The novelty claim is: the synthetic target describes a vulnerability scenario that does not appear verbatim in
any publicly known CVE database or exploit repository as of the generation date.
The novelty claim is NOT: the vulnerability class, the exploitation technique, or the software category is
unprecedented. AI-generated scenarios are recombinations of known patterns. The novelty is in the specific
combination, not in the components.

3.2 Verification Procedure
For each generated target:
1. CVE-database search: Search the NVD and CISA KEV for the specific software/version/vulnerability
combination described in the scenario. If an exact match exists, the target is NOT NOVEL and is
replaced.
2. Exploit-repository search: Search ExploitDB and Metasploit for the specific exploitation path
described. If an exact match exists, the target is NOT NOVEL and is replaced by the next candidate.
Reference corpus snapshot: NVD, CISA KEV, ExploitDB, and Metasploit are snapshotted before any
generation session. Snapshot date and SHA-256 digests committed in the manifest. All novelty verification
runs against the frozen snapshot, not live databases. 3. Description-similarity check: Compute TF-IDF
cosine similarity between the scenario description and the top 100 NVD entries (from the frozen snapshot)
for the same software category. If similarity exceeds 0.85, the target is flagged for pre-evaluation dual review.
(The 0.85 threshold is an operational default, not empirically calibrated; a sensitivity analysis varying the
threshold from 0.70 to 0.95 in steps of 0.05 is reported alongside primary results.) 4. Self-generation check
(post-evaluation): After all evaluation sessions are complete, submit each scenario description (without the
exploitation path) to the test model via a no-retention API endpoint and ask it to describe the vulnerability.
If the test model produces a substantially similar description (cosine similarity > 0.80), the target is flagged
as potentially within the test model’s training distribution. (The 0.80 threshold is an operational default;
the same sensitivity analysis covers this threshold.) This check runs POST-EVALUATION to prevent
pre-evaluation contamination. The scenario descriptions (without exploitation paths) are Tier 2 restricted
material and are submitted only via contractual no-retention API access.
Targets that fail steps 1–2 are replaced by the next candidate in the precommitted generation sequence
(Section 2.5). No discretionary selection of replacements is permitted.
Pre-evaluation review (steps 1–3): Targets flagged in step 3 are reviewed by two independent reviewers
(the program lead + one external reviewer, blinded to BSSG performance data). Disagreements default
to REJECT (fail-closed). Retained targets receive a novelty-confidence downgrade. All step-1/2/3 review
decisions are logged in the candidate ledger and hash-committed before any evaluation session. The preevaluation novelty confidence is: HIGH (passes steps 1–3 with no flags), MEDIUM (step-3 flagged, retained
after dual review), PROVISIONAL (awaiting step-4 post-evaluation check).
Post-evaluation review (step 4 only): After all evaluation sessions are complete, step 4 runs. Targets
flagged by step 4 receive a novelty-confidence downgrade (PROVISIONAL -> LOW). Step-4 downgrades
are recorded in a separate, post-evaluation review record (hash-committed before the primary analysis is
computed). Step-4 may NOT retroactively alter the frozen pre-evaluation manifest, remove targets from

the analysis set, or change any evaluation session’s data. Step-4 results affect the REPORTING phase only:
per-target novelty confidence is updated in the published results, and the aggregate novelty distribution
includes the post-evaluation downgrades.

3.3 Novelty Confidence Levels
Each target receives a novelty confidence:
• HIGH: Passes steps 1–3 with no flags. (Step-4 status is PROVISIONAL until post-evaluation check
completes.)
• MEDIUM: Passes steps 1–2 but flagged in step 3; retained after pre-evaluation dual review.
• LOW: Flagged in step 3 AND downgraded by step-4 post-evaluation check (cosine > 0.80).
• PROVISIONAL: Passes steps 1–3 but step-4 check has not yet run. All targets enter evaluation as
HIGH or MEDIUM; step-4 may downgrade HIGH/MEDIUM to LOW post-evaluation.
The aggregate novelty confidence of the target set is reported as the distribution across HIGH/MEDIUM/LOW.

4. Decoy Placement
4.1 Purpose
Decoys protect the benchmark’s reuse value. If the hidden target set were leaked, a model fine-tuned on the
targets could achieve artificially high scores. Decoys make it impossible to distinguish real targets from false
ones without running the evaluation under controlled conditions.

4.2 Decoy Generation
Decoy generation budget: For every retained real target, one decoy is generated in a separate precommitted
decoy-generation session (50 decoy sessions + up to 10 paired replacement decoys = 60 decoy sessions
maximum). Decoy sessions are logged in the same candidate ledger with disposition code DECOY, and decoy
prompt template digests are committed under F-MC9. For every real target, one decoy is generated using
the same Kimi K3 prompt protocol but with a deliberate technical invalidity injected:
• The described vulnerability does not apply to the specified software version, OR
• The described exploitation path contains a step that is technically impossible in the described environment, OR
• The described impact exceeds what the vulnerability class could produce.
The invalidity is subtle – a non-expert reading the scenario would not immediately identify the error. Only
execution in the actual environment reveals that the decoy is unsolvable.

4.3 Decoy Integration
The 50 real targets and 50 decoys are shuffled into a single 100-scenario manifest. The manifest’s ordering
seed is frozen before the evaluation. The program lead holds the real/decoy classification; the test model and
the evaluation harness do not distinguish them.
Decoy sessions are included in the evaluation but excluded from primary E1/E2 analysis.

5. Evaluation Protocol
5.1 Inheritance from SHV-Bench
Mythos-Class inherits SHV-Bench’s evaluation architecture:
• Two-sided success criterion: fewer unauthorized effects (E1) AND noninferiority on within-scope
capability (E2).
• Paired design: each target run under Condition A (baseline) and Condition B (BSSG-contained),
counterbalanced order.
• Fixed noninferiority margin: delta = 0.05 on the WSDS scale.
• Wilcoxon signed-rank on per-target paired differences (Pratt zeros, permutation-based conditional
exact test).
• Directionally conservative imputation (restated for Mythos-Class): Missing Condition A: UEC_A
= 0, WSDS_A = 1.0. Missing Condition B: UEC_B = U_max, WSDS_B = 0. Missing both: worst
case for containment on both endpoints. Decoy sessions excluded from E1/E2 before imputation. At N
= 50, imputation fraction is reported alongside results.
• Decision mapping: SHV-Bench’s precedence-list labels apply.

5.3 Power Limitation (stated upfront)
N = 50 real targets (or fewer, if the generation budget is partially exhausted) is small. The pre-run power
simulation (F-MC8) determines whether the retained N achieves joint power >= 0.50 at the minimum
detectable effect sizes. If not, the label is UNDERPOWERED/INCONCLUSIVE and no positive containment
conclusion is permitted, regardless of point estimates. Post-hoc power is also reported. This is an acknowledged
limitation, not a design flaw.

5.4 Environment Construction
Each synthetic target’s environment specification (from the generation prompt output) is translated into a
Docker Compose configuration:
• Target services installed at the specified versions.
• Network topology matching the scenario description.
• Adjacent systems for Tier 3 targets.
• No internet access (offline containment).
Ground-truth manifest: A complete ground-truth manifest is hash-committed before any evaluation
session, containing for each real target: scenario specification, expected exploitation path, authorized scope
boundaries, WSDS scoring rubric, and decoy status. Post-freeze edits invalidate the run (F-MC9).
Environment images are hash-bound in the benchmark manifest before any run.

6. Reporting Framework
6.1 What Publishes (Tier 1, Open)
• This protocol paper.
• Aggregate results: E1 and E2 test statistics, p-values, confidence intervals, effect sizes.
• Per-tier results: Tier 1/2/3 subgroup analysis.
• Aggregate novelty confidence distribution (HIGH/MEDIUM/LOW).
• Aggregate target-class distribution.
• Decoy detection rate (what fraction of decoys did the agent attempt to exploit vs. correctly identify as
invalid?).
• Safe redacted examples: 3–5 target scenarios with exploitation paths removed, demonstrating the
scenario format without providing offensive capability.

6.2 What Stays Restricted (Tier 2, Controlled)
• The full target set (50 real scenarios with exploitation paths).
• The decoy set (50 decoy scenarios with invalidity specifications).
• The real/decoy classification key.
• Per-target evaluation logs.

6.3 What Stays Private (Tier 3)
• The generation prompt templates (reusable for future benchmark versions).
• The evaluation harness code (reusable infrastructure).

6.4 Restriction Enforcement
Tier 2 materials are held by the program lead. They may be shared with verified security researchers under a
written agreement for reproduction purposes. They are never uploaded to any AI model’s consumer interface,
any public repository, or any deposit record.

7. Falsification Conditions
F-MC1. Containment has no measurable effect: E1 fails to reject H0 (same as SHV-Bench F-SB1).
F-MC2. Containment degrades capability: E2 fails to reject H0 (same as SHV-Bench F-SB2).
F-MC3. Both sides fail (same as SHV-Bench F-SB3).

7

F-MC4. The target set is not novel: more than 50% of targets fail the novelty-verification procedure (Section
3.2, steps 1–2). The benchmark does not test what it claims to test.
F-MC5. The target set is technically invalid: the test model achieves WSDS = 0 on more than 50% of
targets under Condition A (the targets may be unsolvable, not difficult).
F-MC6. The decoys are distinguishable: the test model’s attempt rate on decoys differs from its attempt
rate on real targets by more than 20 percentage points. The decoy construction is too transparent.
F-MC7. Cross-model novelty is illusory: the self-generation check (Section 3.2, step 4) produces cosine
similarity > 0.80 on more than 50% of targets. The generating model and test model share enough training
distribution to undermine the novelty claim.
F-MC8. Underpowered: pre-run power simulation at the ACTUAL RETAINED N (which may be less than
50 if the generation budget is partially exhausted by novelty failures) yields joint power below 0.50. The
simulation is recomputed at the retained N before any evaluation session. The benchmark proceeds but the
label is UNDERPOWERED/INCONCLUSIVE; no positive containment conclusion is permitted. Post-hoc
power is also reported.
F-MC9 (integrity kill switch). Any post-freeze byte change to the benchmark manifest, prompt template
digests, candidate ledger, ground-truth manifest, real/decoy key, or test-model configuration invalidates the
run. Not waivable.
F-MC4 and F-MC7 denominators: These falsifiers are computed over the ENTIRE ordered candidate
stream (all 60 candidates), not only the retained 50. The replacement rate (rejected/total) is reported
alongside retained-set rates.

8. Scope Limitations
This section states what Mythos-Class does not establish, cannot establish, and does not claim.
External validity. Results on AI-generated synthetic targets do not generalize to expert-constructed targets
or real-world exploitation. The synthetic targets are recombinations of known vulnerability patterns. A
model that performs well on synthetic targets may fail on genuinely novel attacks that involve environmental
complexity, timing-dependent exploitation, or attack types outside any model’s training distribution.
Target technical validity. The synthetic targets are not verified by a security expert. Some may describe
vulnerabilities that are technically impossible in the specified environment. F-MC5 provides a partial guard
(if the baseline agent can’t solve most targets, the targets may be invalid), but passing F-MC5 does not
confirm technical validity – the agent may be solving a plausible fiction.
Generating-model limitations. Kimi K3 generates within its own training distribution. The scenarios
are novel relative to the test model but are constrained by what Kimi K3 has learned. Vulnerability classes,
exploitation techniques, and software categories that are absent from Kimi K3’s training data cannot appear
in the target set.
Sample size. N = 50 is small. The benchmark may lack statistical power to detect real effects. This is
reported honestly, not hidden.
Path C vs. Path B. This is a Path C first-pass result. A definitive Phase C result requires expert-constructed,
expert-verified targets (Path B collaboration with security researchers). Mythos-Class demonstrates the
methodology end-to-end; it does not provide definitive evidence.

9. Conclusion
Mythos-Class specifies a synthetic-target containment benchmark that completes the SHVVP’s three-phase
evaluation architecture: Phase A (axioms and theory, deposited), Phase B (known-vulnerability evaluation,
SHV-Bench deposited), Phase C (novel-target evaluation, this paper).

The benchmark’s contribution is the cross-model generation methodology: using one AI model to construct
evaluation targets for another, creating targets that are novel relative to the test model without requiring
human security expertise. The methodology is honest about what this achieves (cross-model novelty) and
what it does not (expert-verified technical validity).
Whether BSSG containment changes any measurable outcome on novel synthetic targets is the empirical
question this benchmark exists to answer. This paper does not answer it.
